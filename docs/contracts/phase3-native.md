# Phase 3 native gameplay and supervisor contract

Native code is the existing GHost++ at upstream
`6ba90f426e96f80fe013a468d1e07151a510adbe`, distributed as the exact full
`patches/ghostplusplus-modern-linux.patch`. The lock contains the patch SHA256.
The original native publication mailbox, increasing advertisement uptime,
3-second native publish heartbeat and external join tag 15 are preserved.
No BNCS/authentication response is generated by this change.

## Native configuration

The supervisor maps its validated public `gameplay` JSON settings into these
CConfig keys. The AMP helper should write supervisor JSON, not edit GHost
configuration independently. Restart applies these settings. The example is
`config/phase3-native.example.cfg`.

| Public setting | Native CConfig key | Default | Accepted values |
| --- | --- | --- | --- |
| max_players | bot_maxplayers | 12 | integer 2–12 |
| autostart_enabled | bot_autostart_enabled | true | true/false or 1/0; automatic countdown only |
| autostart_players | bot_autostartplayers | 10 | 2–12; <= configured max when enabled; native legacy 0 remains accepted |
| countdown_seconds | bot_countdownseconds | 5 | integer 0–60; existing key preserved |
| vote_enabled | bot_vote_enabled | true | true/false or 1/0 |
| vote_required_percent | bot_vote_required_percent | 60 | integer 1–100 |
| vote_min_players | bot_vote_min_players | 2 | integer 2–12; 1 only for approved AI with minimum one human; <= configured max |
| vote_timeout | bot_vote_timeout | 60 | integer seconds 1–600 |
| vote_cooldown | bot_vote_cooldown | 30 | integer seconds 1–3600 |
| lobby_refresh_enabled | bot_lobby_refresh_enabled | true | true/false or 1/0 |
| lobby_refresh_interval | bot_lobby_refresh_interval | 10 | integer seconds 10–86400 |
| lobby_refresh_mode | bot_lobby_refresh_mode | slot_toggle | slot_toggle only |
| approved preset AI support | bot_lobby_ai_supported | false | true/false or 1/0; native also validates map layout |
| approved preset AI target | bot_lobby_ai_target | 6 when supported | 2–12, bounded by map/operator capacity; effective 0 when disabled |
| approved preset AI skill | bot_lobby_ai_skill | 1 | integer 0–2 |
| approved preset human minimum | bot_lobby_min_humans | 2 | integer 1–12; 1 requires approved AI |

Invalid gameplay configuration disables hosting and exits the update loop;
values are not parsed using permissive `atoi`. Default maximum and autostart
are reduced to the map's true player count and original playable slot count.
The configured maximum never creates additional map slots. The existing
`autohost_startplayers` remains the autohost override; its effective value is
bounded to the map/maximum when assigned to a lobby. Existing `!autostart off`
and validated numeric `!autostart` remain available under the original ACL.

`bot_statusname` defaults to `War3 Dedicated` (1–48 ASCII letters, digits,
space, underscore, dot or dash). It is a public display name, not the realm
account. `bot_externalstatuspath` points to the supervisor feedback file;
feedback TTL is fixed at 10000 ms and is not configurable.

Production-generated paths agreed with the supervisor:

- GHost configuration: `/data/state/native/ghost.cfg`.
- Publication intent: `/data/state/bridge/native-intent.json`.
- Supervisor feedback: `/data/state/bridge/native-feedback.cfg`.

## Commands, votes and countdown

`!vote`, `!status`, `!help` are public and work independently of the configured
legacy command trigger. Slash versions are ignored and are absent from public
help. The real 1.26a client intercepts slash commands before server delivery.

A ballot is one currently connected, non-deleting human PID in an occupied
playable slot. Virtual hosts, fake players, computers and observers/referees
(team/colour 12) never count. A repeated PID cannot add a vote. Ballots are
removed before player deletion, so a reconnect or recycled PID inherits none.
The live threshold is `max(2, ceil(eligible_humans * percent / 100))`.
Only approved AI with minimum/vote minimum one and an actual host-owned
opposing computer can reduce that floor to one. Computers never contribute
ballots or satisfy a real-human automatic-start threshold.
A fresh eligible command starts the 60-second default election. Failure,
timeout, cancellation or a cancelled vote countdown imposes the default
30-second cooldown. Real monotonic timer expiry and test-only timer aging are
both covered by the integration harness.

Admission applies the configured cap to the projected eligible population of
the selected slot, before displacing anyone. A full playable population may
still admit observers/referees when the map provides their slots. Held names
and the owner retain upstream replacement behavior, including when a configured
cap is smaller than the physical map; rejected joins do not kick an incumbent
or change ballots. Scored joins use their retained slot layout and validate a
replacement before kicking. Observer-to-player changes also enforce the cap.

Joins/leaves change the denominator immediately, and leaving voters lose their
ballots. A leave can satisfy the reduced quorum. Dropping below the configured
minimum cancels the vote. Reaching quorum goes through ordinary native
readiness checks. Every occupied human must have 100% map download status;
required identity checks and ordinary ping readiness still apply. Capacity,
unique playable colours, original custom-force/fixed-player assignments,
opposing occupied teams for maps with multiple teams, matchmaking population
and valid HCL settings are checked before countdown. Map-specific script rules
cannot be inferred from metadata and still require real map/client validation.
The built-in `!fakeplayer` PID has no `CGamePlayer` and is exempt only from
human download/identity checks. It remains subject to slot/team/colour/capacity
validation and never counts as a voter or eligible human. An unknown occupied
human PID is still rejected; a fake player does not prevent otherwise valid
vote, administrative or automatic starts.

The countdown snapshots the entire slot composition and the eligible PID set.
Any composition or readiness change cancels it; existing join/leave handlers
also cancel it. The snapshot and quorum/autostart threshold are checked during
each update and again immediately before loading. Vote input cannot start a
second countdown, and repeated game-start callbacks do not load twice. Ballots
clear on loading. The displayed countdown uses seconds, retaining native
500-ms scheduling and configured delay.

While below the automatic-start threshold, the lobby notice reports that
threshold and the missing real humans, followed by the voting population
minimum `max(bot_vote_min_players, NativeMinimumHumans())` and its missing
humans. Computers never reduce either missing-human count. For one human,
custom autostart six and voting minimum four, the notice is:
`Auto-start requires 6 human players (5 more needed). Voting requires at least 4 human players (3 more needed). Type !vote when ready.`
The voting minimum uses `human player` when it is one; remaining counts never
go below zero. Disabled voting instead appends `Voting is disabled.` and no
invitation. A denied `!vote` below its population minimum reports the same
minimum and missing count. Automatic-start notices do not bypass map,
connection, team or other readiness checks; those still run before countdown.
The existing five-second limiter for denied commands remains unchanged.
With preset autostart four and voting minimum two, one human instead sees
`Auto-start requires 4 human players (3 more needed). Voting requires at least 2 human players (1 more needed). Type !vote when ready.`

`!status` sends the public bot name, current lobby/map basename, eligible human
population, map-bounded maximum, autostart threshold, ballots/quorum,
Waiting/Starting/In Game, remaining countdown and process uptime. It also lists
the public commands, so `!help` uses the same response. Status/help and denied
vote replies share a 5-second per-player limiter. No feedback path, realm
endpoint, account name, private IP, credentials or payload is included.

New `!forcestart`, `!cancelvote`, `!botstatus`, `!autohost on|off`, and empty
`!refresh` are inside the original spoofchecked administrator/root/owner and
lobby-lock ACL. `!forcestart` bypasses the ballot, retaining native readiness and
map safety checks. `!autohost` toggles the existing configured autohost mechanism
(one game on enable); a valid preconfigured map/name is required. Existing
realm `!autohost` arguments are unchanged. `!refresh on|off` still controls the
legacy refresh messages. Tag 15 identifies the join route; it does not verify
identity, promote a matching owner name, or grant admin rights. The external
publication mode does not itself supply identity verification, so these admin
commands may remain unavailable to external players. Use the existing verified
control path. No new privileged stdin/stdout control interface is introduced.

## Approved AI and game lifetime

The host owns only computer rows it created, retaining each original empty
row and the expected computer bytes. Humans replace those computers before
admission; rejected joins roll back without changing human rows. Lobby
reconciliation targets `max(0, target - real_humans)` computers, accounting for
unrelated computers and preserving reserved, closed and observer capacity.
It does not refill during countdown, loading or play.

The legacy 60-second "one player left" game-over timer is not started while
approved AI is enabled, the configured human minimum is one, the sole real
human occupies a playable slot, and an actual opposing computer still matches
its host-owned row. This check remains available after upstream releases map
metadata on loading. Native HCL handicap encoding updates the expected owned
row only after verifying its previous bytes. Non-AI, unapproved/minimum-two,
unmanaged-computer and same-team-only cases retain the legacy timer.
Previously started game-over timers and map-statistics game-end handling still
expire normally; the exemption changes only the one-human timer's initiation.

Once all human client connections (including observers) are gone during
loading or play, the native loop saves the game and removes it after the
asynchronous database operation completes. Computer rows do not keep that
match alive. Autohost creates the next configured lobby on its existing
30-second check, subject to capacity and map validity. It does not wait for
AI-versus-AI play to end. Lobby titles remain exact; only the internal/wire
host counter changes.

## Slot refresh

Automatic refresh defaults to **10 seconds**, with accepted configuration
10–86400 seconds. Manual and automatic waves share a process-wide minimum
start-to-start spacing of 10000 ms. The automatic interval is measured from
wave start, not final restoration. A pending wave cannot overlap another;
if its eligible rows take longer than the configured interval, the next wave
waits until the current wave has restored its final row. Failed idle attempts
back off by the configured interval.

At wave start, native snapshots the surplus currently OPEN, empty, playable
human rows. Each row must have `PID == 0`, no computer bit, and playable
team/colour in both the current and original map layout. GHost reservations
are by name: the first free rows are retained for every absent held name and
absent owner. The wave starts at the last surplus free row and visits each
remaining candidate once in reverse order. It changes only slot status to
CLOSED and sends `W3GS_SLOTINFO`. After at least 1000 ms of normal socket-loop
processing it restores the exact original nine bytes and sends slot info
again, then closes the next still-unchanged candidate. A six-row wave takes
about six seconds. No sleep, busy wait or new lobby is used.

Before every restoration and next closure, native compares the saved row
bytes. An unexpectedly changed row aborts the remaining wave without
assigning over an occupant or reopening an intentionally changed slot. All
occupied humans, owned/unrelated computers, observer rows and rows closed at
wave start stay untouched in every captured snapshot. Slot capacity, teams,
colours, races, handicaps, downloads and PIDs are preserved.

A join, slot-admin mutation, added reservation, vote, countdown, loading or
exit restores the current row and cancels all remaining candidates before
its own mutation. Pending connections also cancel the wave, giving admission
priority. Repeated refresh requests cannot restart or shorten it. Failed
automatic-start checks leave the wave running; an actual automatic countdown
restores/cancels it only after all start checks pass. No wave starts during
vote/countdown/loading/play, private/saved/enforced games, pending joins or
without surplus unreserved capacity.

One completed wave increments native refresh count/sequence **once**, after
final restoration, and emits one `[HOSTBOT_REFRESH]` publication hint. There
are no per-row hints. An interleaving cancellation retains the previous
semantics: publish once after safely restoring the current row, except during
exit/loading/play or when publication was explicitly suppressed. A failed
restoration emits no success hint. Completion telemetry records completion
time; the separate start-spacing clock is internal.

Local refresh is not a publication ACK or evidence of iCCup directory ranking
or a list bump. The relay/supervisor owns throttling, correlated publication
requests, ACK accounting and visibility checks. The existing publication
mailbox schema and native publish heartbeat (at least three seconds between
writes) remain unchanged.

## Feedback file: private, bounded, fail closed

The supervisor atomically replaces a CConfig-style file with exactly these
keys (comments/blank lines and surrounding ASCII space/tab/CR are accepted):

```ini
version = 1
observed_monotonic_ms = 123456789
connected = 1
authenticated = 1
publication_accepted = 0
relay_healthy = 1
last_ack_monotonic_ms = 123450000
publication_refresh_count = 7
publication_refresh_successes = 6
publication_refresh_failures = 1
```

Timestamps are unsigned decimal `CLOCK_MONOTONIC` milliseconds, not wall clock,
process-relative uptime, or another host's clock. Counter fields are unsigned
32-bit decimal; timestamps are uint64. Duplicate/unknown/missing fields,
overflow, malformed values, version !=1, boolean values other than 0/1, future
observations, future ACK relative to observation and observation age >10000 ms
are invalid. Zero ACK is valid when there is no accepted publication.

The path must be absolute without dot/empty components; every directory is
opened with `O_NOFOLLOW`. Its final directory must be owned by the native euid
and exactly 0700. The file must be owned by the same euid, a regular file of
1–4096 bytes, exactly 0600, with one hard link and no symlink. Opening uses
`O_NONBLOCK` so a substituted FIFO cannot hang the game loop. The public
directory path/inode is revalidated after reading. Missing, invalid or stale
feedback yields Offline; stale cached counters clear. Feedback is polled at
most once a second for telemetry and read fresh for each allowed status query.

Online means fresh `connected && authenticated && relay_healthy`. Publication
acceptance is deliberately independent: an in-game session normally has no
lobby advertisement. This is display/health feedback only; it changes neither
native player authentication nor game flow.

## Structured stdout

`[HOSTBOT_STATE] ` is followed by one bounded JSON object. It is emitted when
state changes and on an idle heartbeat at most five seconds apart under the
normal native event loop (scheduled at 4000 ms, retaining loop scheduling
margin). Keys:

- `version=1`, `phase=IDLE|LOBBY|COUNTDOWN|IN_GAME` (loading uses IN_GAME).
- `game_name`, `map_name` (basename), `players`, `max_players`,
  `autostart_players`, `votes`, `votes_required`, `countdown`, `host_counter`
  (lower 28 bits), `loading` (boolean). `players` counts real humans only.
- `computer_players` (integer 0–12, actual occupied playable computer rows),
  `ai_target` (integer 0–12), `ai_supported` (JSON boolean).
- `refresh_count`, `refresh_skipped`, `refresh_sequence`,
  `last_refresh_monotonic_ms` (completed or safely cancelled local waves, process lifetime).
- `realm_online`, `feedback_valid`, `publication_refresh_count`,
  `publication_refresh_successes`, `publication_refresh_failures`,
  `last_ack_monotonic_ms` (validated supervisor feedback).
- `active_games`, `uptime_seconds`.

A current lobby takes precedence over the latest active game; when neither
exists the phase is IDLE and lobby population/capacity/identity fields are
empty/zero. Map name/capacity are retained before upstream releases map data on
loading, so status/telemetry remain safe in game. Strings are JSON escaped and
UTF-8 names are preserved; malformed bytes (including overlong encodings,
surrogates, incomplete sequences and values above U+10FFFF) become U+FFFD.
Each string is limited to 255 input bytes, stopping before a valid UTF-8
sequence that crosses the boundary. Console log CR/LF/NUL are escaped before stdout and file output.
One `CONSOLE_Print` call produces
one physical line, so chat/name input cannot forge a second accepted
join/leave or structured-event line. Native local chat retains the exact
`[GAME: <game>] [Local]: <message>` prefix. This protects framing; it does not prove
that a player name is an authenticated realm identity. Consumers must still
validate schema and correlate against the private native publication intent;
stdout never authorizes privileged actions.

After wave completion or a publishable safe cancellation, native emits exactly:

```text
[HOSTBOT_REFRESH] {"version":1,"host_counter":1,"sequence":1}
```

Sequence is monotonic per process, shared by manual/automatic waves. Main merges the actual publisher PID/generation from the strict native
intent before requesting a correlated relay refresh. These extra stdout
events do not alter the publication_intent v1 exact-key schema. No auth/ACK or
visibility is inferred from a local slot toggle.
